# 实现说明：论文未明确处的选择与依据

论文有几处只给了定性描述、没有给出可直接编码的定义。本文件把每一处的
**判断、依据、以及被否决的备选方案**都记录下来，方便复核与答辩时引用。

---

## 1. 标签不进入 Prompt（依据：Fg.2 + 任务定义）

**问题**：论文 Fg.2 的数据结构只有 `uid / string_value / replies`，没有标签字段；
但训练又必须有标签（NR/FR/TR/UR）。

**判断**：标签来自数据集官方的 `label.txt`，**外挂**在数据结构之外，
不进 Prompt、不被 LLM 改写。

**依据**：

1. Fg.2 的字段清单本身就是证据——论文举例的字段里没有类别；
2. 虚假信息检测是**有监督分类**任务，标签是监督信号；若让 LLM 生成标签，
   等于用被测模型制造真值，会污染整个评测；
3. 论文的增强目标始终是"语义一致、表达多样"，属于**改写**任务，
   而不是"判断真假"任务——后者论文明确说 LLM 做不到
   （§4.3："由于 LLM 无法独立判断输入信息的真实性……"）。

**实现**：`DataInstance.prompt_payload()` 只返回三个字段；
`PromptBuilder` 会断言渲染后的 Prompt 不含 `"label"` 键
（测试 `test_prompt_never_contains_label` 覆盖）。

## 2. 文本增强对象：原帖 + 回复都改写

**问题**：论文说"LLM 会对原有信息进行重组与多样化表达"，
但 Fg.4 的示例只展示了 `string_value` 的改写，而 `replies` 里的
"They love him" → "They're fully committed to him" 也被改写了。

**判断**：**原帖与全部回复都改写**，且回复的层级结构、数量、uid 严格不变。

**依据**：Fg.4 的示例同时改写了 `string_value` 与 `replies` 中的回复文本，
且论文强调"replies 中的每条回复保持了原有的层次结构"——
说明回复是被改写的对象，只是结构必须保持。

**实现**：`src/llm/parser.py::check_structure` 校验回复数量与 uid 集合一致；
`merge_augmentation` 递归重建回复树。

## 3. λ 的定义（论文式(8) 只说"CL 性能指标"）

**问题**：论文式(8) 是 `λ_m = β·f_m + (1-β)·λ_{m-1}`，但 `f_m` 具体是什么，
论文只写"作为 CL 性能指标，不仅量化了 CL 模型在虚假信息特征学习任务中的能力，
还能够间接地反映 LLM 数据增强的效果。具体而言，一个较小的……不仅意味着数据增强
产生了语义丰富且有区分度的样本"。

**判断**：默认取 **CL 网络在验证集上的分类准确率**（`f_m = acc`），
并提供 `avg_f1` 与 `inverse_loss` 两种口径开关。

**依据**：

1. 论文说"较小的 f 意味着增强更好"——即 f 越小越好。
   但式(8) 是**加权平均**，若 f 越小越好，λ 会随之变小，
   而式(9) 的 ω 又由 λ 决定……两种符号约定都能自洽，必须选一个；
2. 从论文 Test-time question 1（"增强轮次和基座 LLM 参数量如何影响 CL 模型的
   检测性能"）与 Q2（"多轮联合微调能否持续且稳定提升"）看，
   论文关心的是"增强 → CL 性能"的正向关联；
3. 取准确率有一个实际好处：**量纲天然落在 [0,1]**，
   与式(9) 里 ω 的取值范围一致，不需要额外归一化。

**被否决的方案**：直接用对比损失 `L_CL`。若 `f = -L` 则量纲是无界负数，
需要额外的 `exp`/`sigmoid` 归一化，而论文没有给出这个变换。

**实现**：`compute_lambda_score(metrics, source)`，三种口径都保证"越大越好"；
`inverse_loss` 用 `1/(1+L)` 把损失映射到 `(0,1]`。

## 4. ω 的形式（论文式(9) 只说"由 CL 损失决定"）

**问题**：论文式(9) 给出 `ω_m` 由 CL 的损失值决定，但没有给函数形式。

**判断**：`ω_m = clip(λ_m, ω_min, ω_max)`，默认 `[0.05, 0.95]`。

**依据**：

1. 论文正文明确"ω 由 CL 中的损失值决定"，且"避免单一周期产生过度的影响"；
2. λ 已经是"CL 性能指标的动量平滑值"，直接用它作权重是**最小实现**，
   不引入论文没有的额外超参；
3. 上下界的存在保证：表现最差的一轮仍保留 5% 的话语权（不会被完全遗忘），
   表现最好的一轮也不能完全压制历史（95%）。

**实现**：`compute_omega`；测试 `test_omega_is_clipped_and_monotonic` 验证单调性与截断。

## 5. 论文 docx 中的公式无法可靠还原（重要说明）

**情况**：论文 docx 里的数学公式以 **OLE 对象/MathType** 嵌入
（`word/embeddings/oleObject*.bin` 共 161 个 + 大量 `.wmf` 图片），
纯文本抽取后只剩分号占位符。例如 Algorithm 1 抽取结果为：

```
foreach  do
    ;
    ;
    forall to do
        ;
```

**处理方式**：

1. **正文文字描述优先**：论文对每一步都有文字说明
   （"magnitude 的前 q% 被保留，其余被设置为 0"、"仅保留来自模型且符号与
   聚合后选定符号一致的参数值"），这些描述足以确定算法；
2. **算法原型文献[35]**：论文明确标注 Algorithm 1 的原型是 TIES-Merging
   （Yadav et al. 2024），其三步（Trim / Elect Sign / Disjoint Merge）
   是公开且有官方实现的，本实现严格对齐该结构；
3. **差异处按论文修正**：TIES 原文的符号选举是"绝对值和最大者胜"，
   而论文式(6) 明确是**加权**符号和（权重 ω 由 CL 决定）——
   本实现按论文取加权和，ω 全 1 时自动退化为 TIES 原文行为；
4. **不确定的地方显式标注**：本文件第 3、4 节列出的 λ 与 ω 就是这类情况。

如果你手头有论文的可编辑版本（公式未转成图片），建议核对以下三处：
式(6) 的符号选举、式(7) 的最终合并形式、式(9) 的 ω 定义。
本实现的对应代码分别位于 `elect_sign`、`resolve_scaling`、`compute_omega`，
替换时只需改这三个函数。

## 6. 自举微调的目标：原样本而非增强结果

**问题**：论文说"通过收集 LLM 在训练过程中生成的增强数据，将其作为新的微调
样本来微调 LLM"，但没有说明训练目标（是让模型复现自己的增强输出，
还是别的）。

**判断**：微调样本为 `(增强用的 Prompt → **原样本**的规范化 JSON)`。

**依据**：

1. 若目标是模型自己的增强输出，等于**自我蒸馏**：模型会逐步收敛到
   自己当前的输出分布，把已知的多样性抹平，与"多样性提升"目标冲突；
2. 而"给定实例 → 稳定输出结构正确的 JSON"是增强任务真正的**瓶颈**——
   论文 §4.3 把 FR 类别的性能波动归因于"LLM 无法独立判断真实性"，
   格式与结构的稳定性则是可以通过微调改善的部分；
3. 论文强调"这种方法使得 LLM 能够产生更加丰富和高质量的增强数据"——
   "更丰富"要求模型**不要**收敛到单一输出，这也支持上述判断。

**开关**：`build_finetune_records(target="self")` 提供自我蒸馏对照，
便于做消融。

## 7. 测试集不做增强

**问题**：论文只说"LLM 增强后的数据与原始数据配对后输入至 CL 分类网络"，
没有明确说增强只作用于训练集。

**判断**：**只增强训练集**，验证集与测试集保持原始文本。

**依据**：

1. 论文 §4.1 的数据划分是"70% 训练、20% 测试、10% 验证"，
   增强的目的写在贡献 1 里——"扩展 CL 模型训练维度"，指向训练集；
2. 若对测试集增强，评测对象就变成"LLM 改写过的测试集"，
   与 baseline（BiGCN/BiMGCL 在原始测试集上评测）不可比，
   论文 Table 3/4 的对比也就失去意义。

**实现**：`scripts/train_cl.py::load_datasets` 只为训练集加载
`augmented_round<k>.jsonl`。

## 8. Proposed-6 的微调轮次为推定值

**问题**：论文正文只写"Proposed-6 选用 13B 的 LLM 基座，包含 3 轮数据增强"，
Table 2 的勾选矩阵在 docx 中无法可靠还原。

**判断**：配置里取 `M=2`（增强 3 轮 + 微调 2 次），并在
`configs/experiments/README.md` 显式标注为**推定值**。

**依据**：
Table 7/8 显示"微调轮次的增加也能进一步提升检测准确率"，
且 Proposed-6 在 Twitter15 上取得最高准确率 81.81%——
若 M=0 则它只是"更大的模型 + 同样的增强"，与论文"探索性能上限"的表述
（引入 13B 是为了看上限）不太吻合。

**如需严格对齐**：把 `configs/experiments/proposed-6.yaml` 的
`max_finetune_rounds` 改为 0 即得到"13B + 3 轮增强、不微调"的版本。

## 9. 原帖 vs 回复的 token 预算分配

**问题**：论文没有说明 `string_value` 与 `replies` 拼接后如何截断。

**判断**：原帖优先，回复按 BFS 顺序贪心分配剩余预算；单条超长时保留头部。

**依据**：

1. 原帖是分类的核心依据（`string_value` 是分类主字段），不能被回复挤掉；
2. BFS 顺序贴近信息扩散的层次（论文强调"用户回复中所蕴含的情感倾向和观点
   多样性"），比 DFS 更早纳入被更多人看到的回复；
3. 社交文本的重要信息通常在开头，因此截断保留头部。

**实现**：`data/processors/reply_flatten.py::_allocate_budget`
（原帖上限 = `ceil(sqrt(预算)×4)`，剩余按顺序贪心分配）。
配置项 `data.text_mode` 提供三种模式以支持消融。

## 10. 关于 Proposed-4/5 的 epoch 数设置

论文没有给出每个变体的 epoch 数，只给了"每 T 个 epoch 增强一次"。
本仓库的配置按"增强轮数 × 每轮训练 epoch 数"来确定总 epoch：

| 变体 | w | M | `training.cl.epochs` | 说明 |
|---|---|---|---|---|
| Proposed-1/2/3 | 1/2/3 | 0 | 5 | 单次训练，增强数据预先备好 |
| Proposed-4 | 3 | 1 | 10 | 每 5 个 epoch 一个对齐周期 |
| Proposed-5 | 3 | 2 | 15 | 两个对齐周期 |

依据是 `training.alignment.finetune_interval_epochs`（默认 5）：
微调周期需要至少 5 个 epoch 才能观察到 CL 性能的稳定变化，
因此 `epochs ≈ finetune_interval × (M + 1)`。
这一取值可在配置中直接调整，不影响算法结构。
